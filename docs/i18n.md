# i18n

Stack: `i18next` + `react-i18next` + `i18next-browser-languagedetector`.

## Languages

`supportedLngs: ['en', 'uk', 'ar']`, `fallbackLng: 'en'` (`src/i18n/index.ts`). The language list
and translation resources are both derived from a single place — `src/i18n/resources.ts`:

```ts
export const resources = {
  en: { translation: enJson },
  uk: { translation: ukJson },
  ar: { translation: arJson },
} as const;

export type Language = keyof typeof resources;
export const supportedLanguages = Object.keys(resources) as Language[];
```

Determining the current language — `localStorage` (key `STORAGE_KEYS.language`) → `navigator`, via
`i18next-browser-languagedetector` (`detection.order`/`detection.caches` in `i18n/index.ts`).

The language name in the switcher is an endonym, not a translation (`constants/languages.ts`,
rationale in `docs/conventions.md`).

## RTL

`applyLanguageAttributes` in `src/i18n/index.ts` is called immediately on init and on every
`languageChanged` event:

```ts
function applyLanguageAttributes(lang: string) {
  document.documentElement.dir = i18n.dir(lang);
  document.documentElement.lang = lang;
}
```

`i18n.dir(lang)` is i18next's built-in text-direction lookup, returning `'rtl'` for
`ar` and `'ltr'` for the other supported languages; nothing is hardcoded manually. Switching the
language to `ar` immediately flips the document (`dir="rtl"`) — the CSS doesn't need separate
`[dir="rtl"]` rules for the base layout, since flow/margin/padding in existing CSS modules aren't
tied to a specific side via explicit `left`/`right` anywhere that would cause a mirrored effect
(when adding new CSS, eyeball it against `ar` — the linter doesn't catch this).

## Key typing

`src/i18n/i18n.d.ts` augments `i18next` so that `t('...')` is statically checked against the
real keys of the `en` locale:

```ts
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'translation';
    resources: (typeof resources)['en'];
  }
}
```

`interface`, not `type` — this is declaration merging into someone else's module, the one case
where `interface` is appropriate (see `docs/conventions.md`).

## `satisfies` locale check

`en/translation.json` is the source of truth for the shape of the translation object. `uk`/`ar`
are checked against the same shape by the compiler, with no manual key comparison:

```ts
// src/i18n/resources.ts
type Translation = typeof enTranslation;

ukJson satisfies Translation;
arJson satisfies Translation;
```

If `uk`/`ar` ever gets a typo in a key name, or a key goes missing — `tsc`/`pnpm type-check`
fails on that line, not at runtime on a specific screen.

## Usage

- Components — `useTranslation()` from `react-i18next`, `t('namespace.key')`. No hardcoded
  strings in JSX (this rule has been in effect since phase 5 of the setup plan).
- Outside React (e.g. `src/api/queryClient.ts` for toasts) — import `i18n` directly
  from `~/i18n/index` (not a bare `~/i18n` — see below) and call `i18n.t(...)`.
- Changing the language — `hooks/useLanguage.ts` (`changeLanguage`), not calling
  `i18n.changeLanguage` directly from components.

## Why `~/i18n/index`, not `~/i18n`

`i18n/index.ts` isn't a barrel (no re-exports of other modules) but an entry point with
side-effect initialization (`i18n.use(...).init(...)`). But `no-restricted-imports` (the barrel
guard, see `docs/conventions.md`) matches the `~/i18n` specifier literally, regardless of
whether it's a barrel or not — so side-effect imports use the explicit path `~/i18n/index`
rather than the bare `~/i18n`. `isSupportedLanguage`/`Language`/`supportedLanguages` are moved
into `i18n/resources.ts` specifically so that regular consumers (`hooks/useLanguage.ts` etc.)
never need the bare `~/i18n` import at all.
