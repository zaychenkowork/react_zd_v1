# i18n

Стек: `i18next` + `react-i18next` + `i18next-browser-languagedetector`.

## Языки

`supportedLngs: ['en', 'uk', 'ar']`, `fallbackLng: 'en'` (`src/i18n/index.ts`). Список языков
и русурсы переводов выводятся из одного места — `src/i18n/resources.ts`:

```ts
export const resources = {
  en: { translation: enJson },
  uk: { translation: ukJson },
  ar: { translation: arJson },
} as const;

export type Language = keyof typeof resources;
export const supportedLanguages = Object.keys(resources) as Language[];
```

Определение текущего языка — `localStorage` (ключ `STORAGE_KEYS.language`) → `navigator`, через
`i18next-browser-languagedetector` (`detection.order`/`detection.caches` в `i18n/index.ts`).

Название языка в переключателе — эндоним, не перевод (`constants/languages.ts`, обоснование —
`docs/conventions.md`).

## RTL

`applyLanguageAttributes` в `src/i18n/index.ts` вызывается сразу при инициализации и на каждое
`languageChanged`:

```ts
function applyLanguageAttributes(lang: string) {
  document.documentElement.dir = i18n.dir(lang);
  document.documentElement.lang = lang;
}
```

`i18n.dir(lang)` — встроенный в i18next справочник направлений письма, возвращает `'rtl'` для
`ar` и `'ltr'` для остальных поддерживаемых языков; ничего не хардкодится вручную. Переключение
языка на `ar` немедленно переворачивает документ (`dir="rtl"`) — CSS не требует отдельных
`[dir="rtl"]`-правил для базовой раскладки, так как flow/margin/padding в существующих
CSS-модулях не завязаны на конкретную сторону явным `left`/`right` там, где это могло бы дать
эффект зеркалирования наоборот (при добавлении нового CSS проверяйте на `ar` глазами — линтер
это не ловит).

## Типизация ключей

`src/i18n/i18n.d.ts` аугментирует `i18next`, чтобы `t('...')` проверялся статически по реальным
ключам `en`-локали:

```ts
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'translation';
    resources: (typeof resources)['en'];
  }
}
```

`interface`, не `type` — это declaration merging в чужой модуль, единственный случай, когда
`interface` уместен (см. `docs/conventions.md`).

## `satisfies`-проверка локалей

`en/translation.json` — источник истины по форме объекта переводов. `uk`/`ar` проверяются на
соответствие той же форме компилятором, без ручной сверки ключей:

```ts
// src/i18n/resources.ts
type Translation = typeof enTranslation;

ukJson satisfies Translation;
arJson satisfies Translation;
```

Если в `uk`/`ar` появится опечатка в имени ключа или ключ пропадёт — `tsc`/`pnpm type-check`
упадёт на этой строке, не в рантайме на конкретном экране.

## Использование

- Компоненты — `useTranslation()` из `react-i18next`, `t('namespace.key')`. Никаких хардкод-строк
  в JSX (правило действует с фазы 5 плана сетапа).
- Вне React (например `app/providers/queryClient.ts` для тостов) — прямой импорт
  `i18n` из `~/i18n/index` (не bare `~/i18n` — см. ниже) и `i18n.t(...)`.
- Смена языка — `hooks/useLanguage.ts` (`changeLanguage`), не прямой вызов `i18n.changeLanguage`
  из компонентов.

## Почему `~/i18n/index`, а не `~/i18n`

`i18n/index.ts` — не барел (нет реэкспортов чужих модулей), а точка входа с side-effect-инициализацией
(`i18n.use(...).init(...)`). Но `no-restricted-imports` (защита от барелов, см.
`docs/conventions.md`) матчит specifier `~/i18n` литерально, независимо от того, барел это или
нет — поэтому side-effect-импорты используют явный путь `~/i18n/index`, а не bare `~/i18n`.
`isSupportedLanguage`/`Language`/`supportedLanguages` вынесены в `i18n/resources.ts` специально,
чтобы обычным потребителям (`hooks/useLanguage.ts` и т.п.) bare-импорт `~/i18n` не требовался
вообще.
